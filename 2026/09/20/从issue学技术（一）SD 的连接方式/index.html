从issue学技术（一）SD 的连接方式

从issue学技术（一）SD 的连接方式

在 exfatprogs issue #384 的测试记录中，同一张 SD 卡分别通过 Realtek RTS522A PCIe 读卡器和 Genesys Logic GL3224 USB 读卡器接入 Linux。设备节点分别表现为 /dev/mmcblk... 与 /dev/sd...。为什么同一张卡会出现两条不同的系统路径？本文从硬件连接和 Linux 驱动源码回答这个问题。

Linux 中 PCIe 与 USB SD 读卡器的代码链路

以 Realtek RTS522A（PCIe）和 Genesys Logic GL3224（USB）为例。范围是 Linux 如何发现设备、发起 SD 卡读请求并完成 I/O；不讨论特定应用或文件系统的性能问题。源码以 2026-09-20 查阅的 Linux 主线 master 为依据，函数名可能随内核版本调整。

1. 先看结论

同一张普通 SD 卡插入两种读卡器时，卡与读卡器之间仍使用 SD 协议；变化发生在读卡器与主机之间。RTS522A 通过 PCIe 暴露控制器，Linux 自己管理 SD/MMC 命令并创建 /dev/mmcblkN。GL3224 通过 USB Mass Storage 的 Bulk-Only Transport（BOT）暴露逻辑单元，Linux 对它发 SCSI 块命令，GL3224 固件再把命令转成 SD 卡访问，最终创建 /dev/sdX。RTS522A PCI ID 与驱动 · GL3224 厂商规格

层次 RTS522A：PCIe 读卡器 GL3224：USB 读卡器
主机侧总线 PCIe USB，经 xHCI 主机控制器
Linux 驱动栈 rtsx_pci → rtsx_pci_sdmmc → MMC core → mmcblk USB core → usb-storage → SCSI core → sd
主机发出的存储命令 MMC core 生成 SD 命令，例如 CMD17/CMD18 sd 驱动生成 SCSI READ(10/16)，装入 BOT 命令包
谁处理 SD 协议 Linux MMC 栈和 RTS522A 控制器 GL3224 控制器及其固件；Linux 主机侧看到 SCSI 磁盘
常见设备节点 /dev/mmcblk0p1 /dev/sda1（字母和序号均不固定）
典型插拔入口 控制器卡检测 → mmc_detect_change() USB 枚举/断开或 SCSI 介质状态变化，取决于读卡器行为

名称提醒：这里的 PCIe 是 RTS522A 到计算机的连接方式，并不表示普通 SD 卡以 PCIe/SD Express 模式工作。上游驱动已有部分 SD Express 支持代码，但是否使用该模式取决于卡、控制器及实际协商结果；本文讨论普通 SD 模式。Realtek MMC 主机驱动

2. 设备是怎么出现的

2.1 RTS522A：PCIe → MMC

  1. PCI 子系统枚举到 Realtek 设备。drivers/misc/cardreader/rtsx_pcr.c 的 rtsx_pci_ids[] 包含 10ec:522a，rtsx_pci_probe() 启用 PCI 设备、映射寄存器、配置中断和 DMA，并以 mfd_add_devices() 创建卡槽子设备。源码
  2. drivers/mmc/host/rtsx_pci_sdmmc.c 的 rtsx_pci_sdmmc_drv_probe() 为 SD 槽分配 mmc_host，注册 mmc_host_ops，调用 mmc_add_host()。源码
  3. 插卡事件调用 mmc_detect_change()；MMC core 识别卡、协商总线参数。drivers/mmc/core/block.c 和 queue.c 建立块设备及请求队列，用户通常看到 /dev/mmcblkN 和分区 /dev/mmcblkNpM。主机驱动 · MMC 队列

2.2 GL3224：USB → SCSI

  1. xHCI/USB core 枚举 USB 设备和接口；符合 Mass Storage BOT 的接口绑定 usb-storage。GL3224 官方规格明确支持 BOT，也支持单 LUN 或双 LUN；实际暴露几个 LUN 由产品配置决定。厂商规格
  2. drivers/usb/storage/usb.c 在探测时选择传输方式：USB_PR_BULK 对应 usb_stor_Bulk_transport；随后注册 SCSI host，扫描 LUN。源码
  3. SCSI sd 驱动识别磁盘，建立块设备及请求队列，用户通常看到 /dev/sdX 和 /dev/sdXN。SCSI 磁盘驱动

GL3224 数据手册描述的是 BOT，因此下文按 usb-storage 路径画图。具体机器仍应以 lsusb -t 显示的 Driver=... 为准。GL3224 厂商规格

3. 一次读请求的代码链路

从应用程序读取已挂载文件时，请求先经过 VFS、具体文件系统和页缓存；缓存命中可能完全不访问卡。直接读块设备或使用 direct I/O 时，上层入口不同。两条硬件链路从块层提交的 bio/request 开始才适合逐一对照。blk-mq 文档

flowchart TD
    A[用户程序 read/pread] --> B[VFS / 文件系统 / 页缓存]
    B --> C[块层 bio / blk-mq request]
    C --> D{读卡器连接方式}
    D --> E[MMC block: mmcblk]
    E --> F[MMC core: mmc_request]
    F --> G[rtsx_pci_sdmmc]
    G --> H[rtsx_pci + PCIe DMA]
    H --> I[RTS522A → SD 命令 → SD 卡]
    D --> J[SCSI sd: READ 命令]
    J --> K[SCSI core → usb-storage]
    K --> L[USB BOT: CBW → 数据 → CSW]
    L --> M[USB core → xHCI → GL3224]
    M --> N[GL3224 固件 → SD 命令 → SD 卡]

3.2 GL3224 的读路径

sd_init_command() 将块读请求转换成 SCSI 命令；queuecommand_lck() 唤醒 usb-storage 工作线程；usb_stor_Bulk_transport() 发送 BOT 的 Command Block Wrapper（CBW）、接收数据与 Command Status Wrapper（CSW）。USB 传输最终交给 USB core 和主机控制器驱动。SCSI READ 如何在 GL3224 内部变成具体 SD 命令，是读卡器固件实现，不在 Linux 主机源码中。SCSI 磁盘驱动 · USB SCSI 桥接 · USB 存储线程 · BOT 传输实现 · USB-IF BOT 规范

USB 路径中，主机内存与 xHCI 之间同样使用 DMA；“PCIe 有 DMA、USB 没有 DMA”是不准确的。区别在于 Linux 面对的是 MMC 主机控制器，还是通过 USB/SCSI 接口暴露的桥接设备。USB URB API · GL3224 厂商规格

4. 在 Linux 机器上核对实际路径

下面命令均为只读。先用 lsblk 找到目标设备，再用总线工具核对；不要假定 /dev/sda 或 /dev/mmcblk0 永远对应某个读卡器。

预期：RTS522A 在 lspci -nnk 中出现，驱动通常是 rtsx_pci，SD 槽经 rtsx_pci_sdmmc 进入 MMC 子系统；GL3224 在 lsusb -t 中出现，接口驱动通常是 usb-storage，块设备位于 SCSI sd 栈。TRAN、设备节点和内核日志应互相印证；某些读卡器在无卡时仍保留 SCSI 磁盘节点，是否如此由设备行为和内核处理决定。PCIe 父驱动 · USB 存储驱动
