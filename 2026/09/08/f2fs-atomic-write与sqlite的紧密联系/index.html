f2fs atomic write与sqlite的紧密联系

f2fs atomic write与sqlite的紧密联系

F2FS 使用 COW inode 承接事务新块，COMMIT 再将块映射转交给原文件并执行原子同步。本文结合具体源码、维测日志和测试程序，说明数据库页写入如何形成一次文件原子事务。

1. 事务流程

以一个转账事务为例。数据库中已有 account 表和 transfer_log 表，应用执行：

两条 UPDATE 和一条 INSERT 先修改 SQLite Pager 缓存中的数据库页。例如，它们可能改动 account 表的 B-tree 叶子页、transfer_log 的叶子页、相关索引页以及数据库头所在的第 1 页。这里的具体页数由表布局、索引、空闲空间和 page_size 决定，不能根据三条 SQL 固定推算。

当 SQLite 编译时启用了 SQLITE_ENABLE_BATCH_ATOMIC_WRITE，文件系统又报告支持批量原子写，而且当前事务满足 SQLite 的使用条件时，Pager 在提交阶段设置 bBatch。随后 SQLite 对主数据库文件发出 SQLITE_FCNTL_BEGIN_ATOMIC_WRITE，Unix VFS 将其转换为 F2FS_IOC_START_ATOMIC_WRITE。因此，SQL 的 BEGIN IMMEDIATE 只是在 SQLite 层开启写事务和取得锁；它不直接触发 F2FS 的 START ioctl。

START 成功后，SQLite 通过 pager_write_pagelist() 把本次事务的脏页写到主数据库文件。例如 SQLite 页大小为 4096 字节时，第 1、3、6 页的文件偏移分别为 0、8192 和 20480。写入仍表现为主数据库文件上的 pwrite()，但 F2FS 会为这些 atomic folio 准备 COW 映射。页面发生写回时，新内容写到 COW inode 所管理的新块，原数据库 inode 的持久块映射仍然指向旧数据。

所有待提交页写入成功后，SQLite 发出 SQLITE_FCNTL_COMMIT_ATOMIC_WRITE，Unix VFS 将其转换为 F2FS_IOC_COMMIT_ATOMIC_WRITE。F2FS 等待事务页写回，逐个把 COW 新块转交给原数据库 inode，再同步 node 和恢复信息。ioctl 返回 0 后，SQLite 才继续完成 Pager 的提交状态转换。如果 START、页面写入或 COMMIT 失败，SQLite 会发出回滚原子写请求，并按错误类型决定是否退回普通 journal 路径。

这条路径属于 rollback-journal Pager 的批量原子写优化，不是 WAL 写入流程。它可以避免为当前事务实际写出普通 rollback journal，但 SQLite 是否选择它仍由 SQLite 自身的编译选项、设备能力和事务条件共同决定。

事务时序如下：

    participant Meta as 原 inode 与恢复信息

    SQL->>Pager: UPDATE account(id=1)
    SQL->>Pager: UPDATE account(id=2)
    SQL->>Pager: INSERT transfer_log
    Note over Pager: 生成数据库脏页集合
    SQL->>Pager: COMMIT
    Pager->>IO: START_ATOMIC_WRITE
    IO->>Cow: 创建或复用临时 inode
    IO->>Meta: 保存原大小，设置 FI_ATOMIC_FILE
    IO-->>Pager: 返回 0
    loop pager_write_pagelist 写出每个脏页
        Pager->>Cache: pwrite(数据库文件, 页内容, 页偏移)
        Cache->>Cow: 查询或预留 COW 块映射
        Cache->>Cache: 标脏并设置 atomic folio
    end
    opt 提交前发生数据写回
        Cache->>Cow: 使用 COW dnode
        Cow->>Disk: OPU 写入新块
        Note over Meta: 原文件持久映射尚未提交
    end
    alt 所有页写入成功
        Pager->>IO: COMMIT_ATOMIC_WRITE
        IO->>Cache: filemap_write_and_wait_range
        Cache->>Cow: 写出剩余 atomic folio
        Cow->>Disk: OPU 写入并等待完成
        IO->>Meta: __f2fs_commit_atomic_write
        loop COW 中的有效逻辑块
            Cow->>Meta: 转交新块映射，保存旧地址用于撤销
            Cow->>Cow: 清除已转交的映射
        end
        IO->>Meta: f2fs_do_sync_file(atomic=true)
        Meta->>Disk: 同步恢复信息，必要时执行 checkpoint
        IO->>Meta: f2fs_abort_atomic_write(clean=false)
        Note over Meta: 成功收尾，保留已提交内容
        IO-->>Pager: 返回 0
        Pager-->>SQL: COMMIT 成功
    else 写入或提交失败
        Pager->>IO: ROLLBACK_ATOMIC_WRITE
        IO->>Cache: 清理事务缓存
        IO->>Meta: 清除原子状态，恢复原大小
        Note over Meta: 保留原数据映射
        Pager-->>SQL: 返回事务错误
    end

COW_WRITE 之后，新数据已经有块设备地址，但还不等于事务提交。映射转交也不是一条硬件原子指令：文件系统还依赖同步、node 恢复信息和持久化顺序。源码的 node 写入路径包含 REQ_PREFLUSH / REQ_FUA 处理；本次提交后重启实际观察到了 fsynced dnode 的 roll-forward 恢复。

这里讨论的是掉电恢复语义，不是为其他进程提供数据库隔离。SQLite 仍需要自己的锁和事务控制。F2FS checkpoint 与 SQLite WAL checkpoint 也是不同机制，本程序没有采用 WAL。

涉及的主要源码文件是 file.c、data.c、segment.c 和 node.c。

2.2 页面写入与 COW 写回

prepare_atomic_write_begin() 按文件逻辑页索引寻找 COW 块。若已经预留或写过该页，则复用 COW 映射并设置 use_cow；否则查询原文件块，为 COW 预留新块。原块地址可用于部分页写入时读取未修改的旧内容。

inc_atomic_write_cnt 在新预留处增加计数。因此本次重复写同一页没有增加不同逻辑块数量；它不是 pwrite 调用计数。

复制完成后，f2fs_write_end() 先调用 folio_mark_dirty()，再对原子文件设置 folio_set_f2fs_atomic()。扩展文件时更新原 inode 和 COW inode 的内存大小，original_i_size 仍保留事务起始值。

2.4 取消与状态清理

f2fs_abort_atomic_write() 的 clean 参数决定是否清理事务缓存并恢复文件大小。成功提交传入 ret=0，转换为 clean=false；显式 ABORT 传入 true。

  • clean=false：清除 FI_ATOMIC_FILE、FI_ATOMIC_COMMITTED 等状态，保留刚提交的数据和大小。
  • clean=true：先清理原文件页缓存，再把大小恢复为 original_i_size，避免未提交扩展成为最终文件大小。

该函数同时承担成功收尾和取消清理，因此不能仅凭函数名判断回滚。提交映射阶段失败时还有 revoke_list 撤销路径，错误处理不能简化为“调用 abort 就一定撤销所有持久化操作”。本次验证的是正常提交、显式取消及单打开实例的未提交关闭，没有注入映射或同步错误。

3. 实验

3.1 测试程序

本实验模拟 SQLite Pager 的文件 I/O 事务协议，不执行 SQL，也不生成可由 SQLite 打开的数据库。程序使用单进程和整个文件的 POSIX 写锁，验证页写入、提交与取消；不模拟 B-tree、并发读者及 SQLite 的日志回退。

每个文件初始化 8 页，写入 generation=0 的确定性数据，并 fsync 文件和父目录，建立持久化基线。每页包含校验用页号、代数和尺寸，其余字节也按确定规则填充。验证比较完整页面内容和文件大小，不只比较头部标记。

事务修改程序页索引 0、2、5，类比数据库头、表数据、索引页；然后重复写一次索引 2。程序页索引从 0 开始，类比 SQLite 页号 1、3、6，偏移为 index × page_size。

4. 结论

  1. 本次最新代码的核心是 COW 新块 → 原 inode 块映射转交 → 原子同步及恢复边界，不是旧版 inmem_pages 提交模型。
  2. START 改变后续写入的处理方式；pwrite 仍按主文件偏移进入缓存，写回时 atomic folio 使用 COW inode 的映射。数据可以在 COMMIT 前写出。
  3. COMMIT 先等待数据写回，再转交有效块映射，然后执行同步。成功后的 abort 函数调用是正常清理，clean=false 不丢弃已提交结果。
  4. 本负载中，重复覆盖同一个页没有增加最终转交的不同逻辑块数量；16 KiB 数据库页拆为四个 4 KiB 块，数据库页、内核页和设备请求不能混为一谈。
  5. 实验确认了正常提交、取消、未提交关闭和提交前后 Guest 突然消失时的预期结果。没有测试 COMMIT 内部任意时点中断、故障注入、并发事务、真实 SQLite 日志回退或真实存储设备掉电；这些结果不构成对所有故障模式的证明。
