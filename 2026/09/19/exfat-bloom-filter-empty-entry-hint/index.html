exFAT Bloom filter 与 3-entry、4-entry 空洞复用问题

exFAT Bloom filter 与 3-entry、4-entry 空洞复用问题

本文讨论的是创建文件时的目录空槽复用，不是 Bloom filter 将一个已经存在的文件误判为不存在。对照基线为 exFAT dev 分支的 216426aff8f6；下文的优化实现指在此基础上加入 Bloom filter 和“下一个空槽”提示的补丁。

先把 3-entry 和 4-entry 说清楚

exFAT 的一个普通文件目录项集合包含一个 file entry、一个 stream entry，以及若干 name entry。每个 name entry 最多存放 15 个 UTF-16 code units。因此，通常长度为 1～15 的名称需要 3 个连续目录项，长度为 16～30 的名称需要 4 个。代码中的 exfat_calc_num_entries() 会计算这个数量。

未打补丁的 dev 基线如何寻找空槽

对于一个尚未缓存的新文件名，正常创建路径先查找名称，再分配目录项：

fs/exfat/dir.c 中的 exfat_find_dir_entry() 根据待查名称计算 num_entries，扫描时遇到 TYPE_DELETED 或 TYPE_UNUSED 就调用 exfat_set_empty_hint()。只有连续空槽足以容纳本次需要的目录项集合，或已经延伸到目录尾部，候选提示才会被采用。

所以，查找 4-entry 名称时会看见索引 100～102，但这段空洞只有 3 entries，不会被当作可容纳 4 entries 的位置。扫描继续进行，4-entry 文件最终写到后面。

创建成功后，exfat_create() 调用 inode_inc_iversion(dir)。下次查找另一个新名称时，dev 基线的 exfat_find() 发现目录版本改变，直接使旧空槽提示失效：

接着，exfat_find_dir_entry() 为这个 3-entry 名称重新扫描目录。索引 100～102 现在恰好符合需求，exfat_find_empty_entry() 可以复用它。即使没有依赖上面的版本变化，dev 基线的完整名称扫描也会重新计算空槽候选。

这说明基线的正常路径并非靠一个跨创建操作、永远向前推进的提示保证复用；它依赖重复扫描。代价是：大量不同名称的创建会反复扫描越来越大的目录。

加入 Bloom filter 后，哪个前提变了

优化实现只在目录的已分配容量达到至少 1024 个磁盘目录项后，才尝试在一次完整扫描后惰性构建过滤器；这里的 1024 不是“已有 1024 个文件”。过滤器存在后，查找新名称时如果它给出确定不存在，exfat_find_dir_entry() 会在扫描前返回 -ENOENT：

跳过名称扫描本身是安全的：Bloom filter 的这个结果只说明名称不存在。但扫描原本还承担了另一件事——顺路重新发现靠前的空目录项。跳过扫描后，这个副作用也消失了。

为了避免分配阶段也从头扫描，优化补丁在一次成功的目录项写入后保存“下次从已写入集合之后继续找”的提示。同时，有过滤器时，exfat_find() 不会仅因目录版本变化就清除该提示：

这不是 Bloom filter 的名称查询“假阴性”：新名称确实不存在，-ENOENT 是正确的。错误在于把为 4-entry 请求得出的“前面没有足够空间”结论，错误地沿用到更小的 3-entry 请求，导致目录可能继续增长而不复用已有空洞。

为什么记录 min_entries 可以解决

例如提示来自一次 4-entry 分配，那么早先未被采用的空洞不足以容纳 4 entries；后续仍要 4 entries 或更多时，可以安全地从提示处继续。但后续只要 3 entries，3 < 4，就丢弃提示，让 exfat_search_empty_slot() 从目录开头重新寻找，从而有机会使用索引 100～102。删除或回滚等可能产生新空洞的路径，还必须另外使提示失效。

实现 第二次创建 3-entry 文件时
未打补丁的 dev 基线 正常名称扫描重新发现靠前空洞
无尺寸约束的优化提示 Bloom miss 跳过扫描，旧提示可能跳过空洞
带 min_entries 的优化 新请求更短，舍弃旧提示并从头搜索

关键原则是：“前面没有能放下 4 entries 的空洞”不能推出“前面没有能放下 3 entries 的空洞”。 Bloom filter 省掉名称扫描后，必须由空槽提示自身保存并检查这个条件。
