exFAT Bloom filter 与 3-entry、4-entry 空洞复用问题

exFAT Bloom filter 与 3-entry、4-entry 空洞复用问题

本文讨论的是创建文件时的目录空槽复用，不是 Bloom filter 将一个已经存在的文件误判为不存在。对照基线为 exFAT dev 分支的 216426aff8f6，优化实现取自 v5 工作树的 44356cf7dfa0。下面引用的代码位于 fs/exfat/dir.c 和 fs/exfat/namei.c；含有“省略”注释的片段仅截取与本问题有关的语句。

先把 3-entry 和 4-entry 说清楚

exFAT 的一个普通文件目录项集合包含一个 file entry、一个 stream entry，以及若干 name entry。每个 name entry 最多存放 15 个 UTF-16 code units。因此，通常长度为 1～15 的名称需要 3 个连续目录项，长度为 16～30 的名称需要 4 个。代码中的 exfat_calc_num_entries() 会计算这个数量。

下面固定一组数值，后文每段代码都沿用它。目录簇大小为 32 KiB，每个目录项为 32 字节，所以每簇有 1024 个目录项；假设目录已分配 4 簇，即 p_dir->size=4、total_entries=4096。靠前位置删除了名为 old、占 3 个目录项的文件，留下 [100, 102]；索引 103～2999 均已使用，索引 3000 起是连续未使用空间：

现在先创建一个需要 4 entries 的名称 abcdefghijklmnop（16 个 ASCII 字符），再创建一个需要 3 entries 的名称 abc；两者都是此前未出现过的新名称，例中假设 Bloom filter 对它们均给出确定不存在。前者不能使用 [100, 102]，应当写入 [3000, 3003]；后者应该复用 [100, 102]。索引在这里都是从目录起点开始计算的全局目录项索引，不是某个簇内的偏移。

未打补丁的 dev 基线如何寻找空槽

exfat_set_empty_hint() 不是见到第一个空项就接受提示。它会累计连续空项，直到满足本次的 num_entries，或者空闲区一直延伸到当前目录尾部：

先代入第一个名称 abcdefghijklmnop：num_entries=4。扫描索引 100、101、102 时，candi_empty.eidx=100，count 依次是 1、2、3，始终达不到 4；索引 103 已使用，扫描代码重置 candi_empty。因此 [100, 102] 不能成为 4-entry 请求的有效提示。扫描到索引 3000 的 TYPE_UNUSED 时，count += total_entries - dentry = 4096 - 3000 = 1096，于是记录 ei->hint_femp.eidx=3000。随后 exfat_find_empty_entry() 从 3000 开始验证并写入 [3000, 3003]。

创建成功后，exfat_create() 调用 inode_inc_iversion(dir)。下次查找另一个新名称时，dev 基线的 exfat_find() 发现目录版本改变，直接使旧空槽提示失效：

接着查找第二个名称 abc，这次 num_entries=3。exfat_find_dir_entry() 重新扫描目录；走到索引 102 时，候选值为 eidx=100, count=3, num_entries=3，满足 count == num_entries，于是 ei->hint_femp.eidx=100。之后扫描虽然还会见到索引 3004 起的未使用空间，但前面的提示优先，不会被靠后的提示替换。exfat_find_empty_entry() 取出 eidx=100，再交给 exfat_search_empty_slot()：

因此这次分配会从索引 100 检查连续 3 项，并可复用 [100, 102]。注意 dev 基线的完整名称扫描本身也会调用 exfat_reset_empty_hint() 重算候选；这里不只是依赖 inode 版本变化来保证复用。

这说明基线的正常路径并非靠一个跨创建操作、永远向前推进的提示保证复用；它依赖重复扫描。代价是：大量不同名称的创建会反复扫描越来越大的目录。

加入 Bloom filter 后，哪个前提变了

优化实现只在目录的已分配容量达到至少 1024 个磁盘目录项后，才尝试在一次完整扫描后惰性构建过滤器；这里的 1024 不是“已有 1024 个文件”。对应 exfat_build_name_filter() 的门槛是 exfat_bytes_to_dentries(i_size_read(inode)) < EXFAT_NAME_FILTER_MIN_DENTRIES，其中常量为 1024。

过滤器存在后，查找新名称时如果它给出确定不存在，exfat_find_dir_entry() 会在扫描前返回 -ENOENT。注意下面的返回发生在 exfat_reset_empty_hint(&ei->hint_femp) 之前：

跳过名称扫描本身是安全的：Bloom filter 的这个结果只说明名称不存在。但扫描原本还承担了另一件事——顺路重新发现靠前的空目录项。跳过扫描后，这个副作用也消失了。

为了避免分配阶段也从头扫描，优化补丁在 exfat_find_empty_entry() 中计算“下次从已写入集合之后继续找”的提示：

这个结果先放在调用者的局部变量 next_hint 中，而不是立刻更新 inode。exfat_add_entry() 只有在目录项集合成功提交后才发布它，避免创建失败却跳过仍为空的槽：

具体到本例，删除旧的 3-entry 文件时，优化后的 exfat_unlink() 会调用 exfat_invalidate_empty_hint(dir)，所以第一次创建 abcdefghijklmnop 前没有可用的旧提示。假设 Bloom filter 对该新名称返回确定不存在：名称扫描被跳过；exfat_find_empty_entry() 的局部 hint_femp.eidx=EXFAT_HINT_NONE，exfat_search_empty_slot() 从 dentry=0 开始。它在索引 100 检查连续 4 项时会遇到已使用的索引 103，因此继续寻找，在索引 3000 找到 4 项空槽。

这次分配时传给 exfat_set_next_empty_hint() 的 dentry 是目录全局索引 3000，num_entries=4，因此 next=3000+4=3004。目录总容量仍为 4096 项，局部 next_hint 得到 eidx=3004, min_entries=4；提交成功后才复制到 ei->hint_femp。exfat_find_empty_entry() 返回给调用者的则是簇内偏移（3000 & (1024-1) = 952），不要把这个返回值和保存的全局索引 3004 混淆。

与此同时，有过滤器时，exfat_find() 不会仅因目录版本变化就清除已保存的提示：

接下来查找 abc，Bloom filter 再次给出确定不存在。exfat_find() 虽看到父目录的 i_version 已变化，却因为 ei->name_filter 非空而保留 ei->hint_femp.eidx=3004；exfat_find_dir_entry() 又在重建空槽提示之前返回。所以，在旧的没有请求尺寸约束的实现中，若 exfat_find_empty_entry() 无条件复制这个提示，exfat_search_empty_slot() 就从 3004 而非 0 开始，直接选择 [3004, 3006]：

这不是 Bloom filter 的名称查询“假阴性”：新名称确实不存在，-ENOENT 是正确的。错误在于把为 4-entry 请求得出的“前面没有足够空间”结论，错误地沿用到更小的 3-entry 请求。本例的 [3004, 3006] 尚在已分配的 4096 项之内，所以这一步不立即扩容；但 [100, 102] 被遗留，反复发生后目录可能不必要地增长。

为什么记录 min_entries 可以解决

当前补丁在保存“下一个空槽”提示时，同时记下产生该提示的请求大小：

下一次分配先把局部 hint_femp.eidx 初始化为 EXFAT_HINT_NONE，只有新请求不小于原请求时才复制旧提示：

将具体数值代进去：第一次成功提交后，inode 上记录 ei->hint_femp.eidx=3004、ei->hint_femp.min_entries=4。第二次创建 abc 只需 3 entries，判断 3 >= 4 为假，局部 hint_femp.eidx 仍为 EXFAT_HINT_NONE。于是 exfat_search_empty_slot() 走 dentry=0 分支；到索引 100 时，exfat_get_empty_dentry_set(..., num_entries=3) 看到连续 3 项空槽并返回 0，最终分配 [100, 102]，而不是 [3004, 3006]。

若下一次仍请求 4 entries 或更多，先前扫描已经表明提示之前没有足够容纳 4 entries 的空洞；在没有新删除的前提下，沿用提示是安全的。删除或回滚可能在提示之前制造新的大空洞，所以相关路径仍必须使提示失效。min_entries 解决的是需求从大变小的情况，不能代替这些失效处理。

实现 第二次创建 3-entry 文件时
未打补丁的 dev 基线 扫描时重新记录 eidx=100，写入 [100, 102]
无尺寸约束的优化提示 Bloom miss 后沿用 eidx=3004，写入 [3004, 3006]
带 min_entries 的优化 3 < 4，舍弃 eidx=3004，从头找到 [100, 102]

关键原则是：“前面没有能放下 4 entries 的空洞”不能推出“前面没有能放下 3 entries 的空洞”。 Bloom filter 省掉名称扫描后，必须由空槽提示自身保存并检查这个条件。
