先了解下exfat的16位NameHash

exFAT 的 Stream Extension 目录项中保存了一个 16 位 NameHash。计算时，文件名的 UTF-16 字符先经过卷的 Up-case Table 转成大写形式，因此它符合 exFAT 大小写不敏感的语义。

但 16 位哈希只有 2^16 = 65,536 种结果。它适合做快速过滤和字段完整性校验，不足以在大目录中单独承担低碰撞率的重复名检测。

对每个候选 File dentry set，过滤函数按以下顺序检查：

  1. 第一个目录项必须是 EXFAT_FILE；

  5. 后续目录项必须是 EXFAT_NAME；
  6. 逐段比较所有 UTF-16 字符。

找到匹配项后，exfat_lookup_dentry_set() 会：

  1. 分配 filter.out.dentry_set；
  2. 把匹配到的完整 dentry set 复制进去；
  3. 把匹配项的设备偏移写入 filter.out.dev_offset；
  4. 返回给 handle_duplicated_filename()。

第三步：通过设备偏移区分“自己”和“更早的同名项”

这里比较的不是“某一个指定名称是否撞上另一个指定名称”，而是 N 个名称之间任意两两组合。名称数量为 N 时，一共有：N × (N - 1) / 2

CRC32解决文件名冲突重校验问题

社区新的修改没有改变磁盘格式，也没有用 CRC32 替换磁盘上的 16 位 NameHash。新的设计同时保留两个哈希，各自负责不同任务：

哈希 用途 是否写在磁盘目录项中
exFAT 16 位 NameHash 校验 stream_name_hash 是否正确 是
CRC32 fsck 运行期间筛选疑似重复名 否，仅在内存中

🐸 简而言之，就是社区新增了一个hash值解决原先很容易产生NameHash冲突后重头开始扫描的问题，crc32碰撞概率很低。

核心修改代码

  • tfind() 未找到 CRC32：这是该 CRC32 在当前目录第一次出现，使用 tsearch() 插入；
  • tfind() 找到 CRC32：可能是真正重名，也可能只是 CRC32 碰撞，调用原有精确查找确认；
  • 精确查找发现的目录项设备偏移就是当前项：只是哈希碰撞，不报错；
  • 精确查找先找到另一个同名项：报告重复文件名并进入修复流程。

这里需要区分两个概念：

  1. 至少一次碰撞的概率：只回答整个目录里是否可能出现一对碰撞；
  2. 碰撞次数或碰撞对期望值：决定耗时的完整目录回退可能执行多少次。

对于 70,000 个名称，CRC32 至少发生一次碰撞的概率约为 43.47%，不能说数学上“几乎绝对不会碰撞”。但它的碰撞对期望值只有约 0.57，实际通常是 0 对或 1 对；即使碰撞，也通常只触发一次额外完整名称确认。

同样规模下，旧版 16 位 NameHash 预计约有 26,986 个文件落入已经使用过的槽，因而触发约 26,986 次回退扫描。表中的 37,383.50 是“碰撞文件对”的期望值，不等同于回退文件数；一个槽有三个名称时会形成三对，但后两个名称只各触发一次回退。两种统计方式不同，不过都说明 16 位空间已经高度拥挤。

因此，说“CRC32 冲突比较小”准确的含义是：

在相同目录规模下，CRC32 的期望碰撞次数比 16 位 NameHash 少 65,536 倍，使触发线性目录查找的次数从数万次下降到通常 0～1 次。

CRC32 不是密码学哈希，也没有消除人为构造冲突的最坏情况。它只是为普通文件名提供了足够大的分布空间；真正命中 CRC32 后，代码仍然调用 handle_duplicated_filename() 比较完整名称，确保不同名称的 CRC32 碰撞不会被误报为重复文件。
