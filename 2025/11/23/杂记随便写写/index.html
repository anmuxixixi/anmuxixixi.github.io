exFAT Vendor Allocation Directory Entry：xfstests 回归测试与内核修复

问题背景

exFAT 的一个文件由一组连续的 32 字节目录项描述。常规文件至少包含一个 File Directory Entry（0x85）、一个 Stream Extension Entry（0xC0）和一个或多个 File Name Entry（0xC1）。File Directory Entry 中的 SecondaryCount 记录紧随其后的 secondary entries 数量，整个 entry set 还受 16 位 checksum 保护。

Vendor Allocation Directory Entry 的 EntryType 是 0xE1，属于 benign secondary entry。它不是文件名的一部分，但必须跟着文件的 entry set 一起保存。其核心布局如下：

偏移 长度 字段 含义
0 1 EntryType 0xE1
1 1 GeneralSecondaryFlags bit 0 表示存在簇分配，bit 1 表示 NoFatChain
2 16 VendorGuid 非零 Vendor GUID
18 2 VendorDefined Vendor 自定义数据
20 4 FirstCluster 小端序起始簇
24 8 DataLength 小端序数据长度

因此，rename 和跨目录 move 只能搬迁 0xE1 entry 本身，不能释放它指向的簇；只有 unlink、rmdir 或删除被覆盖的目标文件时，才应释放这些簇。

xfstests 用例设计

用例编号为 exfat/002，由以下文件组成：

  • tests/exfat/002：xfstests 主流程。
  • tests/exfat/002.out：期望输出。
  • src/exfat_vendor_alloc.py：在卸载状态直接解析和修改 exFAT 块设备，用于注入、校验 0xE1 entry 及其簇分配状态。
  • src/exfat_vendor_alloc_test.py：对 Python helper 的合成镜像单元测试。

helper 向 vendor-file 的 entry set 尾部注入两个 Vendor Allocation entries：

  1. GUID 102132435465768798a9bacbdcedfe0f：GeneralSecondaryFlags=0x03，使用两个连续簇，不依赖 FAT chain。
  2. GUID 0123456789abcdeffedcba9876543210：GeneralSecondaryFlags=0x01，使用两个不连续簇，在 FAT 中建立链表。

注入时同步更新 allocation bitmap、FAT、SecondaryCount 和 entry-set checksum，并在每个簇中写入标记数据。这样可以同时检查“目录项是否保留”和“数据簇是否被错误释放”，也能区分 NoFatChain 与 FAT-chained 两条处理路径。

完整操作序列是：

  1. mkfs、挂载 scratch 设备，创建目标目录和 vendor-file。
  2. 卸载后注入两个 0xE1 entries，立即做一次原始设备校验，排除测试数据本身无效。
  3. vendor-file -> vendor-short：文件名仍只需一个 0xC1 entry，覆盖原地 rename 路径。
  4. vendor-short -> vendor-file-with-a-longer-name：文件名需要两个 0xC1 entries，迫使 entry set 扩容和搬迁。
  5. 将文件 move 到 destination/moved-file，覆盖跨目录搬迁。
  6. unlink 文件，校验四个测试簇在 allocation bitmap 中都已清除。

关键证据是 File Directory Entry 开头的 85 02：0x85 是 File Directory Entry，紧随其后的 0x02 是 rename 后的 SecondaryCount。它表明内核重写后的 entry set 只认为自己拥有 Stream 和一个 Filename entry，两个 Vendor Allocation entries 全部被排除。正确值应为 0x04。

期间曾出现过 results/exfat 类型冲突和宿主 ext4 inode checksum invalid 错误，这两类属于测试环境故障，与本内核问题无关。修复环境并重新 mkfs 后，上述 rename 失败仍然可稳定复现。

内核根因

1. exfat_init_ext_entry() 无条件截断 entry set

旧实现只接收根据文件名计算出的 num_entries，并直接执行：

num_entries 只包含 File、Stream 和 Filename entries，完全不包含已存在的 benign secondary entries。因此只要 rename/move 调用此函数，SecondaryCount 就会被重置，entry-set checksum 也会按截断后的范围重算。

原文件名 vendor-file 只需一个 Filename entry，所以基础 entry 数是 3；再加两个 0xE1 entries，实际总数是 5，SecondaryCount=4。rename 到 vendor-short 后仍只需一个 Filename entry，旧代码却把总数改回 3，于是得到日志中的 SecondaryCount=2。

2. 原地 rename 把 Vendor Allocation 当成废弃项删除

旧的 exfat_rename_file() 在旧 entry set 足够容纳新文件名时，会先执行：

对仅有一个 Filename entry 的文件，这个起始下标正好是 3，也就是第一个 Vendor Allocation entry 所在位置。exfat_remove_entries() 不仅把两个 0xE1 entries 标记为 deleted，还会调用 exfat_free_benign_secondary_clusters() 释放其数据簇。对 rename 来说，这两个动作都是错误的。

3. 扩容 rename 和 cross-directory move 没有为 extra entries 预留空间

旧代码用 num_new_entries 调用 exfat_find_empty_entry()，新 entry set 的空间只足够容纳 File、Stream 和 Filename entries。即使后续想复制 0xE1 entries，也没有被分配的位置。随后清理旧 entry set 时又会释放 Vendor Allocation 簇，导致目录元数据和数据分配一起丢失。

4. cross-directory move 的提交顺序可导致源文件丢失

旧 exfat_move_file() 在将新 entry set 写入磁盘之前，就先调用 exfat_remove_entries() 修改了源 entry set。如果目标写入失败，错误路径中的 exfat_put_dentry_set(&mov_es, false) 仍可能把源删除状态提交，从而在没有可用目标副本的情况下丢失源文件。

内核修改设计

修复修改 fs/exfat/dir.c、fs/exfat/namei.c 和 fs/exfat/exfat_fs.h，关键点如下。

  1. 新增 exfat_count_extra_entries()，根据 Stream entry 的 name_len 计算 Filename entry 数，再用完整 entry-set 数量减去 File、Stream 和 Filename entries：

  2. rename/move 按 num_new_entries + num_extra_entries 查找空闲目录项，确保新 entry set 完整容纳所有 benign secondary entries。

  3. 扩展 exfat_init_ext_entry() 的参数，传入旧 entry set 和 extra 数量。函数在更新文件名时，从旧 entry set 尾部复制 benign secondary entries，并以“新文件名 entries + extra entries”重新计算 SecondaryCount 和 checksum。

  4. 原地缩短 entry set 时，extra entries 从旧位置向前移动；复制方向为从前向后，在目标位置不晚于源位置的前提下可避免覆盖尚未复制的源 entry。缩短后多余的旧 entries 再标记为 deleted。

  5. 给 exfat_remove_entries() 增加 free_benign 参数。rename/move 源 entry set 传 false，只删除旧目录记录；unlink、rmdir 和删除被覆盖的目标时传 true，连同 Vendor Allocation 簇一起释放。

  6. SecondaryCount 只有 8 位，对 num_total_entries - 1 > 0xFF 的损坏或过大 entry set 返回 -EIO，防止整数截断后写出自相矛盾的目录元数据。

  7. cross-directory move 调整为先提交目标 entry set，成功后再删除源 entry set。目标写入失败时尝试删除不完整的目标副本，但不释放从源文件复制过来的 Vendor Allocation 簇。

结论

这个问题的本质是内核把“由文件名决定的基础 entry 数”错当成了“完整 entry-set 数”，并把 rename/move 的目录项搬迁误当成了文件删除。修复后，benign secondary entries 作为 entry set 的一部分参与容量计算、复制、checksum 更新和生命周期管理，Vendor Allocation 的数据簇也只在真正删除文件时才会被释放。
