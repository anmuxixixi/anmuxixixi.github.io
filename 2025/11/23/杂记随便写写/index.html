exFAT Vendor Allocation Directory Entry 字段合法性校验

与 rename/move 上游补丁的区别

本节处理的是另一个问题：Linux 已经能识别 EXFAT_VENDOR_ALLOC（0xE1），也会在删除文件时解释其中的分配信息并释放关联簇，但读取 entry set 时只校验了 secondary entry 的排列和大类，没有校验 0xE1 自身的字段是否合法。前一节的 942296784b2a 解决的是合法 benign secondary entry 在 rename/move 中被丢弃；本节解决的是畸形 Vendor Allocation entry 被内核接受、甚至可能进入后续释放路径的问题。

Microsoft exFAT 1.00 规范第 6.2、6.4 和 7.9 节对 0xE1 有以下强制约束：

  1. AllocationPossible 必须为 1。
  2. VendorGuid 不得为全零 GUID。
  3. FirstCluster 只能为 0，或位于 [2, ClusterCount + 1]。
  4. FirstCluster == 0 时，DataLength 必须为 0，并且 NoFatChain 必须为 0。
  5. NoFatChain == 1 时，FirstCluster 必须有效且 DataLength 不得为 0。
  6. DataLength 不得超过整个 Cluster Heap 的字节数。
  7. 对 NoFatChain 连续分配，按 DataLength 向上取整得到的最后一个簇不得越过 Cluster Heap。

GeneralSecondaryFlags 的 bit 2～7 在 Vendor Allocation 中属于 reserved/custom-defined 区域。规范对 reserved 内容的原则是初始化为零、读取方不解释、修改周边内容时保留，因此本补丁不把这些位非零直接判为损坏，避免过度校验破坏兼容性。

FAT FALLOC_FL_KEEP_SIZE 回收阻塞 kswapd：邮件评审与 v2 修改方案

问题背景

2026 年 8 月提交的补丁 fat: reclaim unused KEEP_SIZE clusters on last writer release 试图解决 FAT inode 回收路径可能阻塞内存回收的问题。邮件讨论见：

  • OGAWA Hirofumi 的评审回复

FAT 不在磁盘目录项中持久化“实际已分配长度”。使用 fallocate(..., FALLOC_FL_KEEP_SIZE) 后，文件可以拥有位于逻辑 EOF 之后的 cluster，但磁盘目录项仍只记录原来的文件大小。因此，在内存 inode 消失以前，Linux FAT 必须释放这些未使用的 cluster，否则重新读取目录项时将无法区分哪些 cluster 属于有效文件内容，可能造成空间泄漏或 cluster chain 不一致。

当前内核在 fat_evict_inode() 中执行这一清理：

当 inode eviction 由 kswapd 或 drop_caches 触发，而另一个线程长时间持有 sbi->fat_lock 时，内存回收线程会阻塞在该 mutex 上：

这里真正需要处理的是 fat_lock 的无界持有时间，而不是 KEEP_SIZE reservation 的正常生命周期。

原补丁的处理方式

原补丁为每个 FAT inode 增加 writable struct file 计数：

在 .open 中增加计数，在 .release 中减少计数。当最后一个 writable file 被关闭时，补丁取得 freeze protection、inode->i_rwsem 和 truncate_lock，然后主动调用 fat_free_eofblocks()。后续的异步版本又增加了：

  • 每 inode 的 eofblocks_state；
  • 每 inode 的 work_struct；
  • 每 superblock 的 ordered workqueue；
  • worker 持有 inode 引用以推迟 eviction；
  • unmount 时销毁并 drain workqueue。

这样确实可以让 kswapd 避开部分 EOF-block 清理工作，但代价是改变了用户可见语义：只要最后一个 writable file description 被关闭，预分配 cluster 就会被强制释放，即使系统完全没有内存压力，inode 也不会被回收。

OGAWA Hirofumi 指出的核心问题正是这一点：补丁在“不必要时”也强制释放预分配空间；与其把成本转移到最后一次 close()，更应该约束长时间持有 fat_lock 的线程。

为什么 last-writer-close 方案不理想

1. 改变 KEEP_SIZE reservation 生命周期

现有语义大致是：reservation 至少在 inode 留在内存期间有效，但可能在内存压力导致 inode eviction 后消失。应用如果关闭并重新打开文件，必须重新确认 reservation。

last-writer-close 方案则变成：最后一个 writable file 一关闭，reservation 必定被回收。这样会让频繁执行“打开、预分配、关闭、重新打开”的程序反复分配和释放 FAT cluster，降低预分配的实际价值。

2. 引入与根因无关的生命周期状态

为避免 kswapd 等待一个 superblock 级 mutex，补丁引入了 open/release 计数、inode work、workqueue、freeze protection 和额外 inode 引用。修改范围从 FAT entry 串行化扩展到了 VFS file 生命周期、inode 生命周期和 unmount 流程，审查成本明显增加。

3. 仍未修复通用的长持锁问题

即使 EOF-block 回收不再由 kswapd 执行，其他需要 fat_lock 的线程仍会被同一个长持锁者阻塞。也就是说，workqueue 只是改变了受害者线程，没有消除 fat_lock 临界区过长这一根因。

4. 测试与实现绑定过紧

原 xfstests 用例验证“最后一个 writable fd 关闭后异步回收”，这实际上是在固化新语义，而不是验证真正的问题——长时间持有 fat_lock 时，其他 FAT 操作是否能够获得公平的执行机会。

线程不是因为扫描 FAT 消耗 CPU 而长时间占锁，而是在 fat_ent_bread() 发起 buffer read 时，阻塞于 blk_mq_get_tag()。这说明块设备队列没有可用 request tag；U 盘、USB storage 链路或其底层请求一直没有完成，导致任务进入不可中断的 D 状态。

当前 fat_alloc_clusters() 在调用 fat_ent_read_block() 前已经取得 sbi->fat_lock，所以该任务等待块层资源的全部时间都持有 FAT 文件系统的全局 mutex。只要设备不恢复，fat_lock 就不会释放，kswapd、inode eviction 和其他 FAT metadata 操作会全部排在它后面。

对原 v2 设想的修正

基于这个调用栈，单纯“每扫描若干 FAT block 后解锁并 cond_resched()”不能解决问题。线程阻塞在第一个发生 cache miss 的 fat_ent_read_block() 内部，根本没有机会运行到 batch 末尾。

真正需要建立的规则是：

任何可能等待块设备 I/O 的 FAT block 读取，都不能在持有 sbi->fat_lock 时执行。

v2 仍然应删除 writer 计数和异步 workqueue，保持 KEEP_SIZE 的既有 eviction 语义，但 fat_alloc_clusters() 的修改重点从“限制扫描 batch”改为“把 FAT block I/O 移出锁外”。

partial cluster chain 的所有权

当 nr_cluster > 1 时，本次调用可能已经分配了一部分 cluster，随后为了读取另一个 FAT block 而释放 fat_lock。这些 cluster 已经由 ops->ent_put(..., FAT_ENT_EOF) 标记为非空闲，其他 allocator 不会重复分配，因此仍属于当前调用构造中的私有 chain。

fat_collect_bhs() 会为相关 buffer 增加引用，prev_ent 才能在下一次加锁后继续把前一个 chain tail 指向新 cluster。正式修改需要重点验证：

  • prev_ent 与 fatent 复制 buffer 指针时的引用关系；
  • FAT12 entry 跨两个 sector/buffer 的情况；
  • 读取下一 block 前 fatent_brelse() 是否会提前释放 prev_ent 仍需要的引用；
  • 分配中途发生 -EIO 或 -ENOSPC 时，现有 fat_free_clusters() rollback 是否仍能释放整个私有 chain。

文件系统代码无法让完全失去响应的 U 盘恢复，也不能保证 kswapd 在需要读取未缓存 FAT block 时永远不阻塞。这个补丁修复的是故障放大：一个等待块设备的普通 fallocate() 不应在等待期间占住 superblock 级 FAT mutex，让整个 FAT 文件系统的 metadata 操作都失去进展能力。

后续审计范围

日志证明的 owner 是 fat_alloc_clusters()，所以 v2 应先做这个最小修复。之后还需要审计其他在 fat_lock 内执行 FAT block I/O 的路径：

  • fat_free_clusters()；
  • fat_count_free_clusters()；
  • fat_trim_fs() 中的 FAT read 和 discard；
  • 其他经 fat_ent_read() 进入 sb_bread() 的调用点。

这些路径不能机械地统一解锁：fat_count_free_clusters() 需要解决扫描快照一致性，fat_free_clusters() 需要证明 detached chain 的所有权，带 discard 的释放还必须防止 cluster 被重新分配后遭到旧 discard。它们应在实际调用栈或测试证明必要后分别提交。

功能语义测试

  1. 创建文件并执行 FALLOC_FL_KEEP_SIZE。
  2. 记录 stat -c %b，确认已分配 blocks 大于零且 i_size 不变。
  3. 关闭最后一个 writable fd。
  4. 在 inode 尚未 eviction 时再次 stat，确认预分配 blocks 仍然存在。
  5. 触发 inode eviction 后，确认未使用 EOF blocks 被释放。

这一步保证 v2 没有引入 OGAWA 反对的 last-close 强制回收语义。

阻塞 I/O 与锁隔离测试

  1. 创建并挂载 FAT32 scratch 文件系统。
  2. 预先让测试 inode 和另一组 FAT metadata buffer 保持在 cache 中。
  3. 通过 dm-delay、块层 fault injection 或可控测试设备，让 Thread-A 的 fallocate() 在读取一个未缓存 FAT block 时阻塞。
  4. 用 ftrace/BPF 确认 Thread-A 停在 fat_ent_bread()、submit_bio() 或 blk_mq_get_tag()。
  5. 并发执行只需要已缓存 FAT metadata、但必须获取 fat_lock 的操作。
  6. 旧内核中，该操作应一直等待 Thread-A 持有的 fat_lock；新内核中，它应能获得锁并继续。

测试必须区分“等待 fat_lock”与“线程自己也需要访问故障设备”。如果第二个线程读取了另一个未缓存 FAT block，它在修复后仍可能正常地阻塞于自身 I/O，这不能算补丁失败。最可靠的断言是记录 mutex acquire/release 和 block I/O 调用点，证明 Thread-A 进入块层等待以前已经释放 fat_lock。

建议的补丁拆分

第一轮只提交日志已经证明的最小修改：

不要在同一个 v2 中同时修改 allocator、free、count-free、discard、writer 生命周期和 workqueue。当前证据只要求修复 fat_alloc_clusters() 在全局锁内等待 block I/O 的问题，聚焦这一条调用栈最容易完成并发审查和 A/B 验证。

结论

这次评审揭示的关键不是“异步比同步更好”，而是修复对象选错了。受害者是 kswapd，而实际长持锁者已经由日志确定为 fat_alloc_clusters()：用户态 fallocate() 在 blk_mq_get_tag() 等待故障 U 盘的块层资源，同时占着 fat_lock。

更合理的 v2 是保持 fat_evict_inode() 和 KEEP_SIZE 的既有语义，把 fat_ent_read_block() 这类可能无限等待设备的操作移到 fat_lock 外，并在重新取得锁后验证和修改 FAT entry。这样既直接处理了维护者所说的长持锁一方，也避免为一个块设备 I/O 锁边界问题引入 writer 生命周期和 workqueue 机制。
